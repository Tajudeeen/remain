# Receipt and provenance verifier

Milestone 4 adds a versioned fixture receipt format and an offline verifier. The receipt carries the original planning record, a journal archive, a summary and explicit provenance labels:

| Field | Current meaning |
| --- | --- |
| `mode` | `TEST_FIXTURE` only |
| `planning` | Generated by the synthetic planner |
| `order` | Exported from the local fixture journal |
| `chain` | Assertions supplied by the synthetic settlement test |
| `authentication` | `UNAUTHENTICATED` |
| `signature` | `NOT_REQUESTED` |
| `executionEnabled` | `false` |

The receipt verifier recomputes the plan checksum, binding checksum, journal event hashes and journal tail. It replays event types and ordering, checks request and transaction identities, recomputes the settlement result from the archived evidence and compares the exported summary with the replayed result. It checks event timestamps are monotonic and rejects extra fields, duplicate JSON keys, unsupported values, invalid Unicode, oversized structures and noncanonical numbers.

The canonical format is a small versioned profile used only by Remain. It sorts object keys, represents monetary quantities as decimal strings and uses SHA-256 over the canonical bytes. That digest detects accidental or ordinary edits when the original receipt is retained. A person who rewrites every field and recomputes the checksum can create a different self-consistent fixture file. The verifier has no external trust root, signature authority or chain connection, so consistency is the strongest result it reports.

`MATCHED_FIXTURE` means the archived synthetic evidence satisfies the local accounting rules. It does not prove that a Binance order existed, that a transaction was signed, that a hash was included on BSC or that a block is final. A receipt with `PENDING_ONCHAIN` remains `NOT_RECONCILED`. A later reorg observation can change a prior fixture match to `MISMATCH`.

Use the terminal rehearsal to create and verify a pending receipt:

```sh
npm run rehearse:receipt
```

For a saved receipt file:

```sh
npm run verify:receipt -- ./receipt.json
```

The command reads at most 256 KiB, rejects duplicate keys before parsing, prints a JSON consistency report and exits with code 1 for an invalid receipt. It never makes network requests and never reads credentials. Receipt files can contain fictional addresses and amounts, but must not contain keys, seeds, raw signatures or private wallet data.

The independent tests cover canonical ordering, duplicate keys, invalid numbers, Unicode, size limits, valid serialization, altered plan and binding checksums, modified event payloads, truncated histories, sequence changes, forged summaries, altered provenance and execution flags. The existing 251 tests plus these 13 receipt tests produce 264 tests.

The live gate remains open. Once Binance access is restored, the receipt schema must gain vendor-specific order attribution, wallet signature evidence and independently sourced BSC receipt/log observations. Those fields require new tests and a new provenance profile. The fixture profile must not be relabeled as live.
